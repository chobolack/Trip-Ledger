# Trip-Ledger 規格

旅費記帳程式。第一版重做，起因是朋友傳來的單檔 HTML 雛形
（`Tools/Test.html`，localStorage 單檔版）功能、介面、架構、資料可靠性四項都不滿意。

## 一、定位

- **旅費專用**。不是日常記帳，核心單位是「一趟旅程」。
- **現階段自用**。多人分帳不做，但資料結構預留位置，見 [§6 預留但不做](#六預留但不做)。
- **遊戲外殼**。只做外殼：標題畫面、存檔語彙、科技風視覺。
  不做等級、成就、稱號、連續記帳獎勵這類真實遊戲機制。

## 二、技術決策

| 項目 | 決定 | 理由 |
|---|---|---|
| 前端 | React ＋ TypeScript ＋ Vite | 型別能擋住原版「所有狀態擠一個全域物件」的亂源 |
| 離線 | PWA，離線優先 | 出國漫遊貴、網路不穩，沒網路也要能記 |
| 後端 | FastAPI（Python 3.12） | 使用者已有 FastAPI 經驗 |
| 資料庫 | SQLite 單檔 | 要備份直接拷走檔案，對「資料不放心」最直接 |
| 執行環境 | 先 localhost | 部署之後再決定，但後端從第一天走標準 HTTP API，搬上雲端不用改前端 |
| 同步策略 | 每筆紀錄各自時間戳，後寫者勝 | 單人情境下不需要真正的衝突合併 |

## 三、存檔模型

「存檔」＝一趟旅程。標題畫面只有兩個按鈕。

```
標題畫面
├── 新存檔   → 建立旅程
└── 過往存檔 → 存檔列表
      ├── 進行中（可讀寫）
      └── 已封存（唯讀成績單）
```

- 旅程有 `active` / `archived` 兩種狀態。
- 按「結束旅程」→ 封存，轉成唯讀的結算報告，**不能改**。
- 要改必須先明確「解除封存」，不是隨手就能編輯。
- 進行中的存檔在列表置頂。標題畫面維持兩個按鈕，不加第三個「繼續」。

## 四、幣別與金額呈現

### 幣別選擇

- **一趟旅程只用一種幣別**。不支援一趟跑多國多幣別。
- 幣別用**下拉選單**選，不讓使用者手打代碼。清單在
  `frontend/src/domain/currencies.ts`，要加幣別往那裡補一筆就好，
  各畫面不得自己寫死幣別清單。
- 使用者 2026-11-09 指定先放這五種：台幣、日圓、美金、歐元、人民幣。
  清單含台幣，所以存檔也可以是純國內旅遊（整趟都是台幣）。
- 新存檔預設選日圓——旅費記帳以出國為主。

### 付款方式決定幣別

原使用者（傳 `Tools/Test.html` 雛形的朋友）的觀察，使用者 2026-11-09 轉述：

- **刷卡**：銀行在刷的當下就換好匯，通知直接顯示新台幣 → 本來就是台幣，不必換算。
- **轉帳**：同理，是確定的台幣。
- **現金**：使用者自己去換的外幣 → 用外幣計價。

所以原檔同時提供「外幣／台幣」切換**又**提供「付款方式」是冗餘的，
而且「刷卡 ＋ 外幣」會去乘一個刷卡匯率，但帳單早就是台幣，那個換算是錯的。

本專案做法：**付款方式決定幣別的預設值，但仍可手動覆蓋**。
不寫死的原因：出國前在台灣買機票、網卡、交通票券也算這趟旅費，那些是台幣現金或台幣刷卡。

### 最終呈現：兩個不相加的總額

```
確定台幣花費   NT$ 12,345   ← 刷卡、轉帳
日圓現金花費    ¥ 48,000    ← 原幣顯示，不換算
```

不加匯率欄位。理由是每天匯率不同，原使用者放棄了「用單一匯率抓大概總額」的做法。

> ⚠ **這是原使用者的決定，使用者 2026-11-09 明確表示「大概率會修改」。**
> 不要把這個呈現方式當成不可動的前提。金額的彙總邏輯要集中在一處，
> 改動成本要壓到最低。

### 封存自動換匯（使用者自己加的需求）

2026-11-09 使用者提出：**按下封存時自動抓當日匯率，把現金的部分直接換匯。**

這剛好繞過「每天匯率不同」這個否決理由——封存那一刻只抓一次，
凍結在唯讀成績單上，之後不會再變。

#### 資料來源（已實測）

`https://open.er-api.com/v6/latest/<base>`

- 免費、不需金鑰。
- 回應帶 `access-control-allow-origin: *`，**前端可直接打，不需後端代理**。
- 含 TWD。2026-11-09 實測 `JPY 1 = 0.207095 TWD`，
  與原檔寫死的 `0.2068` 幾乎一致，印證那是當時的即期匯率。
- **台灣銀行牌告匯率（rate.bot.com.tw）已排除**：擋機器人，回傳 Imperva 驗證頁。
  它的現金賣出價其實更貼近實際換鈔成本，若日後要用，得另尋管道。

#### 要處理的狀況

- **離線封存**：抓不到匯率就照常封存，標記「匯率待補」，連線後再補抓。
  不能因為沒網路就不准封存——這個 App 是離線優先的。
- **凍結欄位**：`Trip` 要存下換算當下的匯率、抓取時間與來源，
  不是每次打開成績單都重算。
- **解除封存不清匯率，重新封存也不覆蓋**（使用者 2026-11-09 指定）。
  匯率是那趟旅程當時的實際換匯成本，不會因為回頭補一筆帳就改變。
  清掉的話重新封存會抓到今天的匯率，整趟金額跟使用者原本的紀錄就對不上。
  因此 `sealTrip` 只在 `sealRate` 為 null 時才寫入新抓到的匯率，
  呼叫端也會先檢查、有匯率就連抓都不抓。
  副作用：沒有「強制重抓匯率」的路徑，匯率待補的存檔才會出現那顆按鈕。
- **結束日取「最後一筆花費的日期」，不是按下封存的日期。**
  按封存鍵的時間跟旅程何時結束無關——補記帳、匯入舊資料、
  解除封存後再封存都會讓兩者差很遠。規則算在 `sealTrip` 內部，
  呼叫端不經手，沒有傳錯的餘地。
  沒有任何花費時退回今天；最後一筆早於出發日時退回出發日。

### 原檔匯率的作用（已查明，供決策參考）

原檔 `Tools/Test.html` 有「現金匯率」與「刷卡匯率」兩個欄位，只用於把外幣金額換算成台幣：

- 付現金 → 金額 × 現金匯率
- 刷卡 → 金額 × 刷卡匯率
- 轉帳／交通卡／其他 → 也走現金匯率

分兩個的原因：同樣花 1000 外幣，付現與刷卡實際花掉的台幣不同。現金是換鈔成本；
刷卡是 Visa／Mastercard 結算匯率再加發卡行國外交易手續費（多數卡 1.5%）。
原檔預設值 `0.2068` 與 `0.21` 相差 1.55%，正好就是手續費，印證這個設計意圖。

原檔的問題：要使用者自己查匯率、自己算手續費、手填小數四位；
而且中途再換一次錢（匯率不同）後，這個單一數字就錯了，整趟台幣金額全部跟著偏。

### 待使用者決定的提案

從實際換匯紀錄反推匯率，使用者全程不必知道「匯率」是什麼：

| | 做法 |
|---|---|
| 現金匯率 | 記「換匯事件」：付出 20,000 台幣 → 拿到 96,000 外幣，系統算出 0.2083（已含手續費） |
| 中途再換 | 併入加權平均成本，整趟台幣換算跟著更新 |
| 刷卡匯率 | 拆成「即期匯率」＋「手續費 %」兩格；帳單回來後可逐筆修正成帳單上的真實金額 |

### 統計圖表

使用者 2026-11-09 指定：**圓餅圖，封存時顯示在明細欄位的上方。**

只在封存後出現不是偷懶，是必然的：圓餅圖要有共同單位才有意義，
而把外幣現金換成台幣需要凍結匯率。沒封存就沒有匯率，
硬把台幣與外幣畫進同一個圓餅，只會得到一個看起來合理但毫無意義的圖。

實作約束（都有理由，不要隨手改）：

- 依分類占比，全部換算成台幣。計算在 `domain/money.ts` 的 `categoryBreakdown`，
  算不出來時回傳 null，畫面顯示「匯率待補」而不是畫一張假的圖。
- **切片依金額由大到小排序**（使用者 2026-11-09 指定）。排序做在
  `categoryBreakdown`，不在畫面做——圓餅與圖例必須共用同一份順序，
  分開排遲早會不一致。
- **配色依排名，不依分類**（使用者 2026-11-09 指定，照他提供的參考圖）：
  最大的一片固定是藍色，第二大是琥珀，依序往下。色碼見
  `components/CategoryPie.tsx` 的 `RANK_COLOR`。

  > 已向使用者說明過代價並經其確認：同一個分類在不同存檔、
  > 或金額變動後會換顏色。顏色表示的是「第幾大」而不是「哪一類」，
  > 要認分類得看圖例。**這是使用者的決定，不要自作主張改回依分類配色。**

  連帶後果（已實測，`--pairs all --mode dark --surface #0b1219`）：
  這組色過不了 dataviz 規範的三項檢查——
  亮度帶（`#f4b400` L 0.808、`#00acc1` L 0.682 超出 0.48–0.67）、
  色盲可辨度（紅 `#db4437` ↔ 綠 `#0f9d58` ΔE 4.9，而這兩片剛好相鄰）、
  常人可辨度（青 `#00acc1` ↔ 綠 `#0f9d58` ΔE 14.7，略低於 15）。

  因此**圖例每一列都必須保留分類名稱、金額與百分比**，讓辨識不依賴顏色。
  不要為了版面簡潔把圖例的文字拿掉——那是這組配色唯一的補償機制。
- 切片之間的空隙是用卡片底色描邊做出來的，不是畫外框線；
  描邊寫在 CSS 而非 SVG 的 `stroke` 屬性，因為 CSS 變數在
  presentation attribute 裡不保證解析。
- 圖例每一列都有金額與百分比，所以辨識從不只靠顏色，也等於這張圖的文字版。
- 只有一兩類時不畫圓餅，直接給數字——兩片的圓餅沒有比較意義。
- 小於 1% 的切片在圖上幾乎看不見（會被 2px 空隙吃掉），
  百分比顯示為 `<1%`，實際值由圖例負責呈現。

## 五、現金管理（使用者指定「留，而且要做得更好」）

原版只能登記「出發前換了多少現金」然後扣掉已花的現金。要做得更好的部分：

- 除了出發前換匯，還要能記**途中加換**、**ATM 提現**。
- 隨時對得上皮夾裡實際剩多少錢。
- 外幣現金與台幣現金分開計算。

## 六、預留但不做

以下**不是「這個功能不存在」**，是現階段自用而省略，資料結構要留好位置，日後可補回：

- **多人分帳**：誰付的、誰該分攤、結算誰欠誰。
- **身份識別**：帳號、邀請連結、權限。
- **部署與對外連線**：固定網址、HTTPS、跨裝置同步。

## 七、明確不做

使用者 2026-11-09 勾選「都先不用」：

- 收據拍照
- 行程地點標記
- 行前預算規劃（風格編列、預算與實際比對）
- **預算欄位本身**。使用者 2026-11-09 指定拔掉。
  原因是它比不出東西來：預算是台幣，但旅程進行中的花費分成「確定台幣」與「外幣現金」
  兩個不相加的數字，單位不同；要等封存抓到匯率才算得出完整總額，
  而那時旅程已經結束，預算的提醒作用也過了。
  資料結構裡的 `budgetTwd` 已移除，舊存檔殘留的該屬性不再被讀取。
- 真實遊戲機制（等級、成就、稱號、連續記帳獎勵）

## 八、待確認
