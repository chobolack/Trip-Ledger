# Trip-Ledger 規格

旅費記帳程式。第一版重做，起因是朋友傳來的單檔 HTML 雛形
（`Tools/Test.html`，localStorage 單檔版）功能、介面、架構、資料可靠性四項都不滿意。

## 一、定位

- **旅費專用**。不是日常記帳，核心單位是「一趟旅程」。
- **現階段自用**。多人分帳不做，但資料結構預留位置，見 [§6 預留但不做](#六預留但不做)。
- **遊戲外殼**。只做外殼：標題畫面、存檔語彙、科技風視覺。
  不做等級、成就、稱號、連續記帳獎勵這類真實遊戲機制。

## 二、技術決策

| 項目 | 決定 | 理由 |
|---|---|---|
| 前端 | React ＋ TypeScript ＋ Vite | 型別能擋住原版「所有狀態擠一個全域物件」的亂源 |
| 離線 | PWA，離線優先 | 出國漫遊貴、網路不穩，沒網路也要能記 |
| 後端 | FastAPI（Python 3.12） | 使用者已有 FastAPI 經驗 |
| 資料庫 | SQLite 單檔 | 要備份直接拷走檔案，對「資料不放心」最直接 |
| 執行環境 | 先 localhost | 部署之後再決定，但後端從第一天走標準 HTTP API，搬上雲端不用改前端 |
| 同步策略 | 每筆紀錄各自時間戳，後寫者勝 | 單人情境下不需要真正的衝突合併 |

## 三、存檔模型

「存檔」＝一趟旅程。標題畫面只有兩個按鈕。

```
標題畫面
├── 新存檔   → 建立旅程
└── 過往存檔 → 存檔列表
      ├── 進行中（可讀寫）
      └── 已封存（唯讀成績單）
```

- 旅程有 `active` / `archived` 兩種狀態。
- 按「結束旅程」→ 封存，轉成唯讀的結算報告，**不能改**。
- 要改必須先明確「解除封存」，不是隨手就能編輯。
- 進行中的存檔在列表置頂。標題畫面維持兩個按鈕，不加第三個「繼續」。

## 四、幣別與金額呈現

### 幣別選擇

- **一趟旅程只用一種幣別**。不支援一趟跑多國多幣別。
- 幣別用**下拉選單**選，不讓使用者手打代碼。清單在
  `frontend/src/domain/currencies.ts`，要加幣別往那裡補一筆就好，
  各畫面不得自己寫死幣別清單。
- 使用者 2026-11-09 指定先放這五種：台幣、日圓、美金、歐元、人民幣。
  清單含台幣，所以存檔也可以是純國內旅遊（整趟都是台幣）。
- 新存檔預設選日圓——旅費記帳以出國為主。

### 付款方式決定幣別

原使用者（傳 `Tools/Test.html` 雛形的朋友）的觀察，使用者 2026-11-09 轉述：

- **刷卡**：銀行在刷的當下就換好匯，通知直接顯示新台幣 → 本來就是台幣，不必換算。
- **轉帳**：同理，是確定的台幣。
- **現金**：使用者自己去換的外幣 → 用外幣計價。

所以原檔同時提供「外幣／台幣」切換**又**提供「付款方式」是冗餘的，
而且「刷卡 ＋ 外幣」會去乘一個刷卡匯率，但帳單早就是台幣，那個換算是錯的。

本專案做法：**付款方式決定幣別的預設值，但仍可手動覆蓋**。
不寫死的原因：出國前在台灣買機票、網卡、交通票券也算這趟旅費，那些是台幣現金或台幣刷卡。

### 最終呈現：兩個不相加的總額

```
確定台幣花費   NT$ 12,345   ← 刷卡、轉帳
日圓現金花費    ¥ 48,000    ← 原幣顯示，不換算
```

不加匯率欄位。理由是每天匯率不同，原使用者放棄了「用單一匯率抓大概總額」的做法。

> ⚠ **這是原使用者的決定，使用者 2026-11-09 明確表示「大概率會修改」。**
> 不要把這個呈現方式當成不可動的前提。金額的彙總邏輯要集中在一處，
> 改動成本要壓到最低。

### 封存自動換匯（使用者自己加的需求）

2026-11-09 使用者提出：**按下封存時自動抓當日匯率，把現金的部分直接換匯。**

這剛好繞過「每天匯率不同」這個否決理由——封存那一刻只抓一次，
凍結在唯讀成績單上，之後不會再變。

#### 資料來源（已實測）

`https://open.er-api.com/v6/latest/<base>`

- 免費、不需金鑰。
- 回應帶 `access-control-allow-origin: *`，**前端可直接打，不需後端代理**。
- 含 TWD。2026-11-09 實測 `JPY 1 = 0.207095 TWD`，
  與原檔寫死的 `0.2068` 幾乎一致，印證那是當時的即期匯率。
- **台灣銀行牌告匯率（rate.bot.com.tw）已排除**：擋機器人，回傳 Imperva 驗證頁。
  它的現金賣出價其實更貼近實際換鈔成本，若日後要用，得另尋管道。

#### 要處理的狀況

- **離線封存**：抓不到匯率就照常封存，標記「匯率待補」，連線後再補抓。
  不能因為沒網路就不准封存——這個 App 是離線優先的。
- **凍結欄位**：`Trip` 要存下換算當下的匯率、抓取時間與來源，
  不是每次打開成績單都重算。
- **解除封存不清匯率，重新封存也不覆蓋**（使用者 2026-11-09 指定）。
  匯率是那趟旅程當時的實際換匯成本，不會因為回頭補一筆帳就改變。
  清掉的話重新封存會抓到今天的匯率，整趟金額跟使用者原本的紀錄就對不上。
  因此 `sealTrip` 只在 `sealRate` 為 null 時才寫入新抓到的匯率，
  呼叫端也會先檢查、有匯率就連抓都不抓。
  副作用：沒有「強制重抓匯率」的路徑，匯率待補的存檔才會出現那顆按鈕。
- **結束日取「最後一筆花費的日期」，不是按下封存的日期。**
  按封存鍵的時間跟旅程何時結束無關——補記帳、匯入舊資料、
  解除封存後再封存都會讓兩者差很遠。規則算在 `sealTrip` 內部，
  呼叫端不經手，沒有傳錯的餘地。
  沒有任何花費時退回今天；最後一筆早於出發日時退回出發日。

### 刷卡手續費（使用者 2026-11-09 指定）

海外刷卡會被收國外交易手續費，多數卡 **1.5%**。

**商品金額不含手續費。** 使用者明確指定：商品金額就是商品金額，手續費在明細列與
總計區都是獨立呈現的一筆。所以明細列加起來等於商品金額合計，再加手續費才是總額。

```
皇家禮炮                                    NT$ 3,620
購物 · 海外刷卡
     刷卡手續費 1.5%                          ＋NT$ 54
```

#### 為什麼不做成一個分類

分類回答的是「錢花在什麼上」，手續費不是你買的東西，而且它不獨立存在——
它是從別的分類身上長出來的。做成分類會讓每個真實分類都被低估，
低估的部分全堆在一塊拆不回去的雜項裡。所以**圖表一律畫商品金額，不含手續費**
（`bucketToTwd` 的註解有寫），手續費只在總計區單獨列出。

#### 國內／海外是獨立的一格，不是兩種付款方式

使用者 2026-11-09 指定：**刷卡還是一個類別**，國內／海外在記帳時像幣種那樣
在金額框右上角獨立切換，**預設海外**（這是旅費記帳，刷卡多半刷在國外）。
存成 `Expense.cardRegion`，只有付款方式是「刷卡」時有意義。

曾經做成「國內刷卡／海外刷卡」兩個付款方式，當天就改掉了。理由：

- 付款方式清單會變成兩個概念的乘積，而那份清單剛清乾淨過（拿掉「其他」、
  拆開交通卡）。
- 圖表上「刷卡」會莫名其妙被拆成兩條。實際發生過——北海道那趟的長條圖
  變成「國內刷卡 NT$39,994」與「海外刷卡 NT$34,331」兩條。

**為什麼非得有這一格**：這件事無法從其他欄位推出來。兩種刷卡的帳單都是台幣
（銀行在刷的當下就換好匯），所以出發前在台灣刷機票、訂房、旅平險，跟在國外刷卡，
記下來的資料長得一模一樣，都是「刷卡 ＋ 台幣」。

實證：既有 27 筆刷卡＋台幣裡，**22 筆是出發前刷的**（機票、訂房、網卡、旅平險、
滑雪裝備），那些沒有手續費。一律加 1.5% 的話，光北海道那趟就會憑空多算 NT$546。

用日期猜也不行：廣島九州有「新幹線 NT$1,304」「國際電話 NT$47」記在旅程期間，
但都可能是台灣這邊線上刷的。**只有使用者知道差別，所以讓他在記帳當下就選定**，
不是事後靠程式蒙——這條是決策先行原則的直接應用。

明細列會在刷卡的紀錄後面標「（海外）」或「（國內）」。不標的話，同樣是刷卡
卻有的有手續費子行、有的沒有，使用者看不出原因。

#### 費率存在存檔上，而且可以改

`Trip.cardFeePct`，新存檔預設 `1.5`。跟 `sealRate` 同樣的理由：換一張卡、
換一家銀行費率就不同，而已經記完的旅程不該因此變動。

存檔頁有輸入框可以改，**但封存後不顯示**——改它會動到已凍結的總額，
跟封存匯率同一條理由。要改就先解除封存。

**預設一律 1.5，已封存的存檔與匯入的舊備份也一樣**（使用者 2026-11-09 指定：
不要匯入後還得先解除封存去改費率）。

⚠ 代價：**已封存旅程的總額會變動**，比以前高出那筆手續費。這跟「封存＝凍結」
是衝突的，使用者知情並選了這個——理由是那些手續費本來就付了，
只是以前沒算進去，不是憑空多出來的錢。

要讓某趟不算手續費，解除封存後把費率改成 `0`。

#### 舊資料的地區一律設成「海外」

使用者 2026-11-09 指定：**原本檔案的刷卡全部當海外。**
schema v9 的遷移與 `backup.ts` 的 `normalize` 都把沒有 `cardRegion` 的紀錄
一律補成海外，不去還原任何舊值裡的國內／海外之分。

兩個理由：使用者指定；以及這樣**停在哪個 schema 版本的裝置都會得到同一個結果**
（照舊值還原的話，跑過中間版本的裝置會跟沒跑過的分岔）。

⚠ 代價：既有 27 筆刷卡＋台幣裡，有 22 筆是出發前在台灣刷的機票、訂房、網卡、
旅平險，那些其實沒有手續費，現在會被標成海外。因為費率一律預設 1.5，
**那 22 筆會被實際多算手續費**，不只是標籤不對。目前**沒有編輯已記帳目的功能**
（見 §8 待確認），所以改不了，只能刪掉重記。

#### ⚠ 遷移只會跑一次（2026-11-09 的教訓）

v6 的轉換規則在同一天內改過兩次，而**遷移只會跑一次**——先載入過中間版本的
裝置會停在舊規則。實際發生過：北海道那趟被拆成國內刷卡 11 筆、海外刷卡 14 筆，
而後來改 `modernizePaymentMethod` 對那些已經轉完的資料完全沒有作用。

所以**改已經發布的遷移對既有資料沒有用，必須另外加一版補正**（v7、v8 就是這樣來的）。
更好的做法是像 v9 那樣，讓新遷移的結果與「裝置停在哪一版」無關。

`db.ts` 裡也留了警告：v8 那種「把 0 無條件翻成預設值」的寫法只有在
欄位剛誕生、值必然是遷移自己寫的那一天成立。日後不能再這樣寫。

### 原檔匯率的作用（已查明，供決策參考）

原檔 `Tools/Test.html` 有「現金匯率」與「刷卡匯率」兩個欄位，只用於把外幣金額換算成台幣：

- 付現金 → 金額 × 現金匯率
- 刷卡 → 金額 × 刷卡匯率
- 轉帳／交通卡／其他 → 也走現金匯率

分兩個的原因：同樣花 1000 外幣，付現與刷卡實際花掉的台幣不同。現金是換鈔成本；
刷卡是 Visa／Mastercard 結算匯率再加發卡行國外交易手續費（多數卡 1.5%）。
原檔預設值 `0.2068` 與 `0.21` 相差 1.55%，正好就是手續費，印證這個設計意圖。

原檔的問題：要使用者自己查匯率、自己算手續費、手填小數四位；
而且中途再換一次錢（匯率不同）後，這個單一數字就錯了，整趟台幣金額全部跟著偏。

### 待使用者決定的提案

從實際換匯紀錄反推匯率，使用者全程不必知道「匯率」是什麼：

| | 做法 |
|---|---|
| 現金匯率 | 記「換匯事件」：付出 20,000 台幣 → 拿到 96,000 外幣，系統算出 0.2083（已含手續費） |
| 中途再換 | 併入加權平均成本，整趟台幣換算跟著更新 |
| 刷卡匯率 | ~~拆成「即期匯率」＋「手續費 %」兩格~~ → **已做**，見〈刷卡手續費〉。剩「帳單回來後逐筆修正成帳單上的真實金額」還沒做 |

### 統計圖表

使用者 2026-11-09 指定：**圓餅圖，封存時顯示在明細欄位的上方。**

只在封存後出現不是偷懶，是必然的：圓餅圖要有共同單位才有意義，
而把外幣現金換成台幣需要凍結匯率。沒封存就沒有匯率，
硬把台幣與外幣畫進同一個圓餅，只會得到一個看起來合理但毫無意義的圖。

實作約束（都有理由，不要隨手改）：

- 依分類占比，全部換算成台幣。計算在 `domain/money.ts` 的 `categoryBreakdown`，
  算不出來時回傳 null，畫面顯示「匯率待補」而不是畫一張假的圖。
- **切片依金額由大到小排序**（使用者 2026-11-09 指定）。排序做在
  `categoryBreakdown`，不在畫面做——圓餅與圖例必須共用同一份順序，
  分開排遲早會不一致。
- **配色依排名，不依分類**（使用者 2026-11-09 指定，照他提供的參考圖）：
  最大的一片固定是藍色，第二大是琥珀，依序往下。色碼見
  `components/CategoryPie.tsx` 的 `RANK_COLOR`。

  > 已向使用者說明過代價並經其確認：同一個分類在不同存檔、
  > 或金額變動後會換顏色。顏色表示的是「第幾大」而不是「哪一類」，
  > 要認分類得看圖例。**這是使用者的決定，不要自作主張改回依分類配色。**

  連帶後果（已實測，`--pairs all --mode dark --surface #0b1219`）：
  這組色過不了 dataviz 規範的三項檢查——
  亮度帶（`#f4b400` L 0.808、`#00acc1` L 0.682 超出 0.48–0.67）、
  色盲可辨度（紅 `#db4437` ↔ 綠 `#0f9d58` ΔE 4.9，而這兩片剛好相鄰）、
  常人可辨度（青 `#00acc1` ↔ 綠 `#0f9d58` ΔE 14.7，略低於 15）。

  因此**圖例每一列都必須保留分類名稱、金額與百分比**，讓辨識不依賴顏色。
  不要為了版面簡潔把圖例的文字拿掉——那是這組配色唯一的補償機制。
- 切片之間的空隙是用卡片底色描邊做出來的，不是畫外框線；
  描邊寫在 CSS 而非 SVG 的 `stroke` 屬性，因為 CSS 變數在
  presentation attribute 裡不保證解析。
- 圖例每一列都有金額與百分比，所以辨識從不只靠顏色，也等於這張圖的文字版。
- 只有一兩類時不畫圓餅，直接給數字——兩片的圓餅沒有比較意義。
- 小於 1% 的切片在圖上幾乎看不見（會被 2px 空隙吃掉），
  百分比顯示為 `<1%`，實際值由圖例負責呈現。
- **兩張圖都不含刷卡手續費**，畫的是商品金額。所以圓餅圖標題的總計會比
  總計區的「完整總額」少了手續費那一截，這是對的，不是漏算。
  見〈刷卡手續費〉。

  圓餅圖讀數列下方因此標著「圓餅圖不含手續費」（使用者 2026-11-10 指定，
  取代原本的「共 N 類，點切片可篩選下方明細」）。**不寫出金額**——
  兩個數字擺在一起反而要讀者自己做減法。顯示條件跟原本那行一樣：
  只在沒有切片被點選或滑過時出現，選中時這一行要讓位給該分類的數字。

#### 點圖篩選明細

使用者 2026-11-10 指定：**長條圖也要能像圓餅圖那樣點了就篩選下方明細。**

- 分類與付款方式是**兩個獨立的篩選，同時成立就是交集**。
  刻意不做成「選一個就清掉另一個」——那會讓使用者點了付款方式之後，
  分類的高亮無聲消失。
- **圖表本身永遠顯示完整占比**，不跟著篩選縮水。點一下圖就只剩一片的話，
  就沒得比了。
- 篩選的取消按鈕放在明細標題列，不在圖裡：解除封存後圖表會消失，
  篩選卻還留著，放圖裡就沒辦法取消。
- 筆數只在最後報一次。那是交集後的結果，掛在任一顆篩選按鈕上
  都會被看成那個條件單獨的筆數。

## 五之二、刪除就是真的刪除

使用者 2026-11-09 指定：**刪除直接從資料庫移除，不寫墓碑。**

原本的做法是刪除只寫 `deletedAt`（墓碑），讀取時濾掉。那是離線優先的標準做法，
目的是把「我離線時刪掉了什麼」同步給別的裝置——硬刪什麼都不留，就沒東西可以帶出去。

**被推翻的理由**：這個程式沒有後端（`backend/` 只有一份 README），
也不打算做自動同步，所以那個目的永遠不會兌現。而墓碑當下唯一的實際效果是負面的：

> 刪除會把 `updatedAt` 蓋上當下的時間，於是墓碑永遠比備份檔新。
> 合併模式匯入時那筆會被無聲略過——使用者刪掉一趟旅程、想拿別人的檔案換上去，
> 結果只看到「略過 67 筆」，完全不知道為什麼進不來。
> 2026-11-09 使用者實際踩到這個狀況。

**付出的代價（使用者知情並接受）**：

- 匯入一份還含有那趟旅程的舊備份，它會被當成新資料加回來。
  匯入畫面會回報「新增 N 筆」，看到再刪一次即可。
- 刪除的意思不會傳遞給別人。你刪一筆重複資料、把檔案傳給朋友，
  他匯入後那筆仍然在他那邊——要靠你們自己講。

**實作**：

- `repo.ts` 的 `deleteTrip`／`deleteExpense` 真的 `delete`。
- IndexedDB schema **v5** 的遷移把既有墓碑一次清掉。不清的話舊墓碑會繼續擋匯入。
  這一步不可逆：墓碑裡還留著被刪紀錄的內容。
- `applyBackup` 忽略備份檔裡的墓碑（兩種模式都忽略），不讓資料庫重新長出墓碑。
- **`deletedAt` 欄位留著不要拆**，備份格式版本也維持 `1`。
  舊版程式與別人裝置上的舊檔還帶著墓碑，要讀得懂才能正確忽略；
  版本不動，檔案才能繼續跟還沒更新的裝置互傳。
