# 備份檔格式

App 的「備份 → 匯出」產生的 JSON，也是匯入時唯一接受的格式。

**寫這份文件的原因**：2026-11-09 發生過一次——使用者把一份匯出檔當成範例給朋友，
朋友請他的 AI 照著做其他旅程的轉換。結果猜對了，但那是運氣。
範例檔不是規格，猜錯了程式也不會報錯，只會讓統計默默少算。
要轉換試算表的人請看這份，不要逆向工程範例檔。

## 整體結構

```json
{
  "format": "trip-ledger-backup",
  "version": 1,
  "exportedAt": "2026-11-09T07:14:22.031Z",
  "trips": [ ... ],
  "expenses": [ ... ],
  "cashEvents": []
}
```

`format` 與 `version` 必須如上。三個陣列都必須存在，可以是空陣列。

## trips

```json
{
  "id": "okinawa2026",
  "name": "2026沖繩",
  "currency": "JPY",
  "status": "archived",
  "startedOn": "2026-03-18",
  "endedOn": "2026-03-23",
  "createdAt": "2026-11-09T07:14:22.031Z",
  "updatedAt": "2026-11-09T07:14:22.031Z",
  "deletedAt": null,
  "sealRate": 0.203079,
  "sealRateAt": "2026-03-23T00:00:00.000Z",
  "sealRateSource": "csv-import（由原始記帳的折合台幣反推）",
  "ownerId": null
}
```

| 欄位 | 規則 |
|---|---|
| `id` | 字串，整個裝置上唯一。**決定重複匯入會不會變成兩份**，見〈編號〉 |
| `name` | 非空字串 |
| `currency` | 三個大寫英文字母的 ISO 代碼。App 的下拉選單只有 TWD／USD／EUR／JPY／GBP／CNY／AUD，但匯入接受任何三碼 |
| `status` | `active`（進行中，可記帳）或 `archived`（已封存，唯讀結算畫面） |
| `startedOn` | `YYYY-MM-DD`。**出發日由你決定，程式不會推算**，見〈出發日〉 |
| `endedOn` | `YYYY-MM-DD` 或 `null`。`active` 的存檔應為 null |
| `createdAt` / `updatedAt` | ISO 8601 字串 |
| `deletedAt` | 填 `null`。有值的紀錄匯入時會被忽略，見〈墓碑〉 |
| `sealRate` | 1 外幣＝幾台幣。大於 0 的數字，或 `null` 代表匯率待補 |
| `sealRateAt` / `sealRateSource` | ISO 8601 字串／自由文字，沒有就填 `null` |
| `cardFeePct` | 海外刷卡手續費率（%），0 或正數。多數卡填 `1.5`。**沒這欄的舊備份匯入時補 `1.5`**，所以匯入後的總額會比檔案原本的數字高出那筆手續費。要讓某趟不算就填 `0` |
| `revising` | 選填布林。已封存的存檔是否正在修訂（明細暫時可寫）。**匯入時一律忽略、當成 `false`**——那是單一裝置上的暫時狀態。手寫備份檔不用填 |
| `budgetTwd` | 選填。這趟的預算（台幣），大於 0 的數字；沒設填 `null` 或不寫 |
| `estRate` / `estRateAt` | 選填。預算用的估算匯率（1 外幣＝幾台幣）與抓取時間。**跟 `sealRate` 是兩回事**，只影響預算面板，不影響結算。手寫備份檔不用填，程式會自己抓 |
| `ownerId` | 固定 `null`。多人共用的預留欄位，現階段不用 |

## expenses

```json
{
  "id": "okinawa2026-e031",
  "tripId": "okinawa2026",
  "spentOn": "2026-03-20",
  "category": "購物",
  "title": "刮鬍刀",
  "paymentMethod": "刷卡",
  "amountKind": "foreign",
  "amount": 10822,
  "note": "",
  "createdAt": "2026-03-23T11:59:30.000Z",
  "updatedAt": "2026-11-09T07:14:22.031Z",
  "deletedAt": null,
  "payerId": null
}
```

| 欄位 | 規則 |
|---|---|
| `id` | 字串，唯一 |
| `tripId` | 對應某個 trip 的 `id` |
| `spentOn` | `YYYY-MM-DD` |
| `category` | **只能是這六個**：`餐飲`、`交通`、`景點門票`、`購物`、`住宿`、`其他` |
| `title` | 項目名稱，可以是空字串（畫面會改顯示分類名） |
| `paymentMethod` | **只能是這五個**：`現金`、`刷卡`、`轉帳`、`西瓜卡`、`悠遊卡`（**沒有「其他」**）。舊值 `交通卡`、`其他`、`國內刷卡`、`海外刷卡` 匯入時會自動換掉 |
| `cardRegion` | `overseas` 或 `domestic`，**只有刷卡用得到**。沒這欄一律補 `overseas`，見〈刷卡手續費〉 |
| `amountKind` | `twd`（金額是台幣）或 `foreign`（金額是該趟的外幣） |
| `amount` | 大於 0 的數字，單位由 `amountKind` 決定 |
| `note` | 自由文字，沒有填 `""` |
| `createdAt` | ISO 8601。**同一天之內的顯示順序由它決定**，見〈同日順序〉 |
| `deletedAt` | 填 `null`。有值的紀錄匯入時會被忽略，見〈墓碑〉 |
| `payerId` | 固定 `null`。多人分帳的預留欄位 |

### 常見的對應錯誤

| 原始資料常出現 | 要轉成 |
|---|---|
| Suica、ICOCA、PASMO、西瓜卡 | `西瓜卡` |
| 一卡通、iPASS、悠遊卡 | `悠遊卡` |
| 飲食、食物、吃 | `餐飲` |
| 門票、景點 | `景點門票` |
| 紀念品、伴手禮 | `購物` |
| TWD／台幣 | `amountKind: "twd"` |
| JPY／日圓／其他外幣 | `amountKind: "foreign"` |

注意 `category` 有 `其他`，但 `paymentMethod` **沒有**。
真的遇到放不進那五項的付款方式（電子支付、禮券、他人代墊），
請回報以便把清單加回來，不要自己塞一個新字串——會被當成未知值。

### 已淘汰的值

| 舊值 | 會被換成 | 由來 |
|---|---|---|
| `交通卡` | 外幣→`西瓜卡`、台幣→`悠遊卡` | 2026-11-09 之前沒有區分哪一張卡 |
| `其他`（付款方式） | `悠遊卡` | 原記帳者確認過：那些「其他」都是悠遊卡，只是當時試算表沒分這一類 |

**舊備份檔照樣匯得進來**，匯入時自動換掉；裝置上既有的資料也會在升級時一併轉換。

新做的檔案請直接用現行的五個值。

### 認不得的值會怎樣

匯入驗證會擋下來。萬一還是混進去（直接改過資料庫之類），
統計**不會丟掉它**，而是保留原值自成一類排在最後——
圓餅與橫條的占比永遠加總到 100%，金額永遠對得上總計區。

**寫錯合法值會怎樣**：匯入會被擋下並指出是第幾筆、哪個欄位、合法值有哪些。
（在加上驗證之前，錯的值會讓那筆錢從統計圖裡消失而不報錯——這就是寫這份文件的由來。）

## cashEvents

現金管理功能尚未實作，**一律填 `[]`**。

## 編號

`id` 決定匯入時的比對結果：

- 裝置上沒有這個 id → 新增
- 有，且檔案裡的 `updatedAt` 比較新 → 更新
- 有，且裝置上的比較新 → 略過

所以轉換試算表時請用**固定推導**的編號（例如 `hokkaido2025`、`hokkaido2025-e001`），
不要用隨機 UUID。固定編號的檔案重複匯入不會長出兩份；隨機編號的會。

## 出發日

**程式不會從明細推算出發日。** `startedOn` 寫什麼就是什麼。

轉換舊資料時，行前訂的機票與住宿通常比實際出發早好幾天。
要把出發日定成「飛出去的那天」還是「開始為這趟花錢的那天」由你決定——
畫面上那個欄位寫的是「出發」。

可以參考的判斷線索：第一天出現**外幣現金**支出，通常就是入境日。

封存時的**結束日**則是自動的，取最後一筆花費的日期。

## 同日順序

明細在同一天之內是「`createdAt` 新的排在上面」。

要讓顯示順序跟原始試算表的上下順序一致，請讓 `createdAt` **由上往下遞減**：

```js
const base = Date.parse('2026-03-23T12:00:00.000Z');
createdAt: new Date(base - i * 1000).toISOString()   // i 是列號
```

## 墓碑（已停用，但欄位要留）

`deletedAt` 有值代表這筆已刪除。**2026-11-09 起刪除改成真的從資料庫移除**，
所以這個程式匯出的備份檔裡，`deletedAt` 永遠是 `null`。
見 [規格.md](規格.md)〈刪除就是真的刪除〉。

欄位本身**不要從格式裡拔掉**，有兩個理由：

- 舊版程式匯出的檔案、以及別人裝置上舊版匯出的檔案，裡面還有墓碑。
  匯入時要讀得懂才能正確忽略它們（會回報「忽略 N 筆舊版的已刪除紀錄」）。
- 備份格式版本維持 `1`，檔案才能繼續跟還沒更新的裝置互傳。

轉換新資料時全部填 `null` 就好。

## 匯入的兩種模式

| | 行為 | 用途 |
|---|---|---|
| 合併（預設） | 比 `updatedAt`，新的勝出 | 兩台裝置互相匯入對方的備份 |
| 覆蓋 | 以檔案為準，不比時間 | **以這個檔案為準**，例如拿別人的檔案來核對自己這份 |

兩種模式都會忽略檔案裡的墓碑，不寫進資料庫。

合併模式唯一會讓人意外的結果是「略過」——本機版本不比檔案舊就不覆蓋，
而使用者可能正是想拿這個檔案蓋掉手上這份。所以 `skipped > 0` 時畫面會說明原因
並給出覆蓋的按鈕。
